# 01 — Architecture

## 1. Context
Kestrel ingests hazard signals from free sources, decides alert levels with explicit, testable rules, merges them with community reports and official SACHET alerts, and delivers localized alerts through free channels. Microservices are justified by **(a) fault isolation** (flood path survives other feeds failing), **(b) different load shapes** (fan-out is quiet for weeks then spikes; report intake is unpredictable), **(c) different data/cadence per feed**. Each microservice is deployed as an individual **AWS Lambda function**; scheduled ingestion is triggered by **EventBridge Scheduler**. No VM, no Docker Compose in production.

## 3. Phased pipeline (contract-stable)

| Phase | alert path |
|---|---|
| MVP | `flood-ingest → rules-engine → alert-fanout` (fanout subscribes to `decision-flood/heat/aq` SQS queues) |
| 2 | `… rules-engine → signal-fusion → alert-fanout` (fanout switches to `fused-*` SQS queues) |
| 3 | `… signal-fusion → alert-composer → alert-fanout` (fanout switches to `composed-*` SQS queues) |

The SQS queue binding is a **config property** (`fanout.input-queue-*`). The payload is always `AlertEvent` (see doc 03). `alert-fanout` renders its own message from templates when `content` is absent (MVP/P2) and uses composer's `content` when present (P3).

## 4. Service ownership matrix

| Service | Owns (source of truth) | Replicates (DynamoDB local copy) | Publishes (SNS) | Consumes (SQS) |
|---|---|---|---|---|
| subscriber-registry | locations, coordinators, subscriptions, consent | — | `LocationUpserted/Deleted`, `SubscriptionChanged` | — |
| flood-ingest | flood thresholds, forecast snapshots, snap status | locations | `FloodSignal`, `FeedStatus` | `Location*` |
| rules-engine | rule config, alert state, alert history | — | `AlertEvent(stage=DECISION)` | `FloodSignal`, `HeatSignal`, `AqSignal` |
| alert-fanout | deliveries, broadcasts, templates | subscriptions, locations | `DeliveryReceipt`, `BroadcastCreated` | `AlertEvent`, `Subscription*`, `Location*` |
| cap-ingest | official CAP alerts, location mapping | locations | `OfficialAlertSignal`, `FeedStatus` | `Location*` |
| report-intake | reports, moderation | locations | `ReportAccepted`, `ReportUpdated` | `Location*` |
| signal-fusion | fused status per (location,hazard) | locations | `AlertEvent(stage=FUSED)` | `AlertEvent(DECISION)`, `Report*`, `OfficialAlertSignal` |
| heat-ingest | heat normals, snapshots | locations | `HeatSignal`, `FeedStatus` | `Location*` |
| aq-ingest | AQ snapshots, station cache | locations | `AqSignal`, `FeedStatus` | `Location*` |
| alert-composer | templates, composed alerts, static CAP XML | — | `AlertEvent(stage=COMPOSED)` | `AlertEvent(FUSED)` |
| audit-evaluation | audit log, observed events, backtests, feedback | — | — | everything (read-only SQS taps) |

**Rule:** a service that needs another service's data at *runtime on the critical alert path* must use a local DynamoDB replica fed by events (so that service stays up when the owner is down). REST calls to other services (via CloudFront/Lambda Function URLs) are allowed only for non-critical paths and must be wrapped in circuit breakers.

## 5. Key flows

### 5.1 Flood alert (MVP)
1. EventBridge Scheduler triggers `flood-ingest` Lambda. It fetches ensemble discharge per monitored point (batched), computes per-day exceedance share vs 2/5/20-year thresholds, stores a snapshot in DynamoDB, publishes `FloodSignal` to SNS → SQS `rules-flood`.
2. `rules-engine` Lambda is triggered by SQS `rules-flood`, runs `FloodRule` → candidate severity; the **state machine** applies persistence (consecutive runs), hysteresis (de-escalation), cooldown, stale-data guard; on a transition writes alert history + outbox item to DynamoDB, relay publishes `AlertEvent(DECISION)` to SNS.
3. `alert-fanout` Lambda is triggered by SQS `fanout-decision`, applies **auto-send policy** (default: auto only if severity ≥ WARNING), plans recipients from its local DynamoDB subscription replica (location + hazard + minSeverity), dedupes (DynamoDB conditional write + TTL), renders per-language message with provenance wording, enqueues `DeliveryTask`s to SQS delivery queues (SEVERE first via message group or attribute ordering).
4. Channel Lambda workers send: Telegram (DynamoDB token bucket), Web Push (VAPID), Mock. Receipts recorded + published to SNS.
5. Dashboard queries Lambda Function URLs → shows state, provenance, data age, history.

### 5.2 Manual one-tap broadcast
Coordinator picks location(s) + hazard + severity (or starts from an active alert) → `POST /broadcasts/preview` (per-language/channel previews, recipient count, estimated send time) → `POST /broadcasts` with `Idempotency-Key`. Same delivery pipeline; message includes coordinator note + provenance label. A **WhatsApp share link** is generated client-side from the preview text.

### 5.3 Community report (Phase 2)
Resident → `report-intake` Lambda (validate, spam-limit via DynamoDB rate counter, geo-match) → SNS `ReportAccepted` → `signal-fusion` Lambda counts corroborating reports within radius/time → may upgrade provenance to `MODEL_PLUS_REPORTS`. **Reports never raise severity by themselves** (D-16); they surface in the coordinator inbox for human action.

### 5.4 Official alert (Phase 2)
EventBridge Scheduler triggers `cap-ingest` Lambda to poll SACHET RSS → fetch CAP 1.2 XML → map hazard/severity/area → SNS `OfficialAlertSignal` → `signal-fusion` sets `OFFICIAL_CONFIRMED`, may relay official alerts (source labelled "Official alert via SACHET"). The CAP feed (static JSON/XML) is regenerated and uploaded to S3 / served from Amplify/Cloudflare Pages.

## 6. Local replicas (event-carried state transfer)
- Ingest Lambdas keep `monitored_point` replicas in their own DynamoDB tables from `LocationUpserted/Deleted` events via SQS; at startup they bootstrap via `GET /internal/v1/locations` (CloudFront-blocked from public; Lambda-to-Lambda direct invocation or internal REST call) **or** a seed CSV (`infra/seed/locations.csv`) so ingestion never depends on registry availability.
- `alert-fanout` keeps `subscriber` replicas in DynamoDB from `SubscriptionChanged` events (carries a monotonically increasing `version`; apply only if higher) and reconciles every 10 minutes via EventBridge Scheduler + `GET /internal/v1/subscriptions/changes?cursor=`.
- At send time fanout re-checks `status=ACTIVE` on its DynamoDB replica; unsubscribe events must propagate in seconds via SNS.

## 7. Failure behaviours (must be tested)
| Failure | Required behaviour |
|---|---|
| aq/heat feed down | flood path unaffected; feed shows `DOWN` on dashboard; no alert from stale AQ/heat data beyond max-age |
| Open-Meteo flood down | retry/backoff; last-good snapshot kept in DynamoDB; `dataAge` grows; rules-engine holds existing state, never *escalates* on data older than `maxDataAge` (default 36 h); dashboard shows stale banner |
| registry down | ingestion and fanout continue (DynamoDB replicas); new subscriptions fail gracefully |
| SQS / SNS delivery failure | Lambda retry + DLQ; no lost or duplicated alerts (idempotent inbox in DynamoDB) |
| Telegram 429 | respect `retry_after`; DynamoDB token bucket backs off; severe-first ordering preserved |
| Telegram 403 (blocked) | mark channel `BLOCKED` for that subscriber in DynamoDB; stop retrying |
| DynamoDB throttling | exponential backoff in SDK; ingest call budget falls back to DynamoDB conditional write with retry |
| Poison message | to SQS DLQ after N retries; CloudWatch alarm + metric |

## 8. Non-functional targets
- Flood alert latency (decision → first send queued): < 5 s p95.
- Telegram throughput ≈ 25–30 msg/s (free limit) → 50,000 subscribers ≈ 28 min; **severe first, tiered by location**.
- Mock sender: 50,000 subscribers delivered; record time-to-first and time-to-last; **initial target < 60 s** (own target; adjust after measurement).
- Cost: all within AWS free tier indefinitely (Lambda 1M req/month, DynamoDB 25 GB + 25 RCU/WCU, SQS 1M req/month, SNS 1M publishes/month, CloudFront 1 TB + 10M req/month, Cognito 10k MAU, EventBridge Scheduler 14M invocations/month).
- Frontend: initial JS ≤ 200 KB gzip; Lighthouse PWA ≥ 90, Performance ≥ 80 on mid-range Android profile.
